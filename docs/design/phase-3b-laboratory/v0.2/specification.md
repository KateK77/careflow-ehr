# Revised requirements v0.2

**Design revision only; implementation is not approved.** These requirements amend the [preserved v0.1 specification](../v0.1/specification.md); unchanged requirements continue to apply. They are future acceptance obligations, not claims of working laboratory functionality.

## V2-01 — Explicit MVP finalization

The current assigned active Lab Staff member may enter, save, preview and finalize the report, even when they are the original entry actor. Require explicit finalization confirmation, synthetic-data confirmation, aggregate/draft versions and durable command UUID. Preserve original entered_by/created_at, last draft editor, finalizer/published_at, edit_version and publication revision. A reassignment changes who may next finalize but never rewrites earlier authorship. No UI calls this independently verified, clinically validated or production-grade separation of duties. Existing required values/units/absence reasons and specimen/time checks remain.

## V2-02 — Explicit covering-physician assignment

Separate immutable ordering_physician from an order's current review assignment. Original submission creates assignment sequence 1 to the ordering physician. If the current responsible physician becomes inactive or no longer has Physician membership, an active Administrator with explicit `labs.reassign_review_responsibility` permission may preview and confirm reassignment to an active Physician, with nonblank reason, current order/assignment versions and audit. The target cannot be FrontDesk, Nurse, Lab Staff or an inactive/non-Physician account merely because an Administrator chose it.

Preserve prior assignment rows, original ordering identity, report content and all acknowledgements. New assignment sequence requires review of the current publication even if that same person acknowledged it in a previous assignment epoch. No automatic acknowledgement, impersonation, silent reassignment or automatic return to a reactivated original physician. The assignee receives lab-order/report access and acknowledgement only, not patient-chart membership, SOAP, history authoring, encounter reopening, order creation or cancellation on the original physician's behalf. Reassignment is permitted for submitted, fulfilled and withdrawn orders, not drafts/cancelled orders. If no eligible target exists, show Responsibility unresolved and retain the review item. Reassigning an active eligible physician requires a separate policy and is not part of this minimal workflow.

## V2-03 — Specimen and cancellation boundaries

One non-rejected specimen attempt per order, permanent rejected history, unique accessions and monotonic attempt numbers remain. Cancel is an original-ordering-Physician action on draft/submitted orders only, with reason and no receipt on **any** attempt and no publication. Once an attempt has ever been received, later rejection never restores cancellation eligibility. Cancelled orders are terminal, preserving actual specimen states and excluding them from actionable queues.

Assigned Lab Staff may reject a collected/received attempt only before any publication and with no active result draft; abandon a draft explicitly first. Recollection is a Nurse action against a submitted order after prior rejection, including after encounter completion. Never reset a rejected attempt. After first publication, no recollection, receipt metadata correction or specimen reassignment on that order; use correction for report data or withdrawal for invalid reporting. After withdrawal, specimen history is frozen and any replacement testing needs a new authorized order. All race outcomes are explicit in [states](states.md).

## V2-04 — Typed JSON is the preferred MVP storage

Use strictly validated immutable typed JSON snapshots, not untyped dictionaries accepted from the browser. Register validators by `(schema_version, publication_kind)`; freeze catalog schema/unit/bounds in report snapshots. Enforce numeric-string precision/range, controlled codes, exact units, unknown-key rejection, maximum size and value-versus-absence exclusivity. Unknown schema versions cannot be saved or published. Historical decoders remain available; changing a validator's meaning requires a new schema version, not rewriting old payloads. All-not-performed reports have explicit reasons and no invented performed timestamp.

Keep relational FKs, versions, publication status/kind, timestamps and uniqueness constraints outside JSON. Cross-row state/context and JSON semantics require transactional service validation, not a claim that SQLite constraints validate every nested value. Never compare decimal strings lexicographically for numeric trends. Normalized components or a validated query projection are future alternatives requiring separate design/migration review; do not create them now.

## V2-05 — Append-only withdrawal / entered-in-error notice

The current assigned active Lab Staff member may explicitly withdraw the current final/corrected report for an error, with preview, reason code/text, target publication ID, order version, confirmation and command key. If a correction draft exists, it must first be explicitly abandoned; withdrawal does not silently discard it. Withdrawal atomically appends a new immutable LabResult publication with kind=withdrawal/status=withdrawn, supersedes the exact current publication, has no result values/performed timestamp, updates the current-publication pointer and marks the order withdrawn. Preserve first fulfilled_at, every old report value/status/actor/time, original context, specimen and acknowledgements. No delete, patient reassignment or retrospective mutation of a published row.

The withdrawal notice becomes current; no prior numeric result is automatically promoted as a replacement. A withdrawn order is terminal for reporting, not cancelled, submitted, normal, negative or not-performed. No correction/recollection/unwithdrawal after withdrawal. The notice appears in the responsible Physician's review worklist, even if the old report was acknowledged. Review records acknowledgement of the **withdrawal notice**, not clinical validity, and never restores an order/result. If responsibility is unresolved, retain the notice for explicit reassignment. A replacement report requires a new properly authorized order.

## V2-06 — Safe chart presentation and history

Current chart/encounter summaries show Report withdrawn — not a usable result, reason category, time and whether the notice has been reviewed; do not show withdrawn values as current or absent/negative. Ordinary report-error history can display previous values only behind an explicit Historical withdrawn report warning for authorized readers. A context-error reason (suspected wrong patient/specimen) quarantines the entire withdrawn chain: ordinary clinical readers, including the covering physician, receive safe notice/provenance and prior acknowledgement actor/time/assignment metadata, but not prior values, free-text review comments or unrestricted reason text in chart, history, comparisons, search, audit snapshots or error responses. Assigned Lab Staff and Administrator with explicit `labs.view_quarantined_report` permission may inspect quarantined payloads within authorized audit/requisition views. No report or specimen is reassigned to another patient to repair context. Signed SOAP and encounter/check-in provenance remain untouched.

## V2-07 — Review identity, versions and races

Current review status is derived from `(current_publication, current_review_assignment)`, not just reviewer user ID or result revision. Only that assignment's active Physician may acknowledge the displayed current final/corrected/withdrawal publication; server derives reviewer and review kind. Unique publication+assignment acknowledgement; exact command replay creates no duplicate rows/events. A new assignment, correction or withdrawal creates a new obligation and does not erase earlier reviews. Backend capability/context checks precede receipt disclosure; stale publication or assignment fails with 409/403 as appropriate.

Serialize all lab writes with the **original ordering physician's** provider lock, then order and relevant children, so coverage changes do not change the lock key or bypass existing completion synchronization. Recheck active actor/permissions, assignment and current pointer inside the transaction. Reassignment, correction, withdrawal, receipt, cancellation and acknowledgement races must yield the deterministic outcomes in [states](states.md). LabStaff and Physician assignments are separate dimensions.

## V2-08 — Staged delivery and approval gates

Use the [proposed 3B-1/3B-2/3B-3 plan](increments.md), each with separately approved scope, functional Issue/branch, PR, CI and manual UAT checkpoint. Technical schema dependencies may precede a later screen only where explicitly documented; no phantom controls or claims that an incomplete lifecycle is production-ready. Do not create any implementation branch/functional Issue or begin code/migration work under this design revision. All v0.1 exclusions, synthetic-data controls and signed-document preservation obligations remain.
